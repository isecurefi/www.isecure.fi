Create independent payment batches, edit their payments during the day, then generate exact bank-file XML. Your application signs and submits the file separately through the [File Exchange API](https://www.isecure.fi/wsapi_v2/#operation/UploadFile). Processing generation does not send or approve a payment.

**Beta · Production · Separate product entitlement required.** This reference covers the deployed payment operations and session exchange. Bank-format availability and qualification come from `paymentExportProfileCatalog.list()`; SDK method availability alone does not imply a deployed capability.

With SDK 5.1.0, the standard production URL automatically selects the Processing audience. A custom `processingAudience` is not required.

## Prepare a payment file

1. **Choose a format:** `paymentExportProfileCatalog.list()` lists bank formats. Check availability and qualification.
2. **Save the configuration:** `paymentExportProfiles.configure()` creates a configuration when no ID is supplied. Keep its ID, resource version and returned `capability`. Each tenant can have several configurations, including several for the same bank and account. `list()` lists saved configurations; `get({ payment_export_profile_id })` reads one.
3. **Start a batch:** pass that exact capability to `paymentBatches.createDraft()`. Every batch has its own ID and payments. Several batches may be built concurrently for one or several banks.
4. **Edit and validate:** use `addPayments()`, `updatePayment()` and `removePayments()` with the latest resource version. Amounts are decimal strings. `validate()` checks the exact revision.
5. **Finalize and generate:** `finalize()` freezes the revision. `generateFile()` renders that revision and its bound configuration. The request repeats their IDs/versions as consistency checks; it cannot select a different bank at download time. No second approver is required for this generation-only path.
6. **Sign and send separately:** the SDK verifies generated bytes against the returned integrity metadata. Sign for the destination File Exchange account and upload explicitly. Never automatically retry an upload with an unknown outcome.

For OP, `debtor_bank_agreement_id` is the OP C2B agreement's **maksatustunnus**, 9–11 characters. Preserve its exact form and leading zeros. `initiating_party_customer_id` is unused by OP and may be omitted. Profile-fixed currency, account scheme, BIC and country can be supplied by the server; contradictory explicit values are rejected. Use the bank/account identifiers appropriate to the destination test or production environment, regardless of where the XML was generated.

To revise a configuration, supply its ID and `expected_resource_version` in the body. An update affects only work bound to that configuration. It does not overwrite another configuration; existing drafts do not silently switch to its newer revision. Reconcile stale work explicitly.

## Separate approval workflow

If your application uses Processing approval, finalize, call `submitForReview()`, obtain the distinct authorized review through `paymentApprovalRequests.decide()`, and release through `paymentExports.release()`. Download using the returned artifact authority. This is separate from generation-only access; neither path proves bank acceptance.

## Retention and examples

Drafts, finalized revisions and audit history remain stored; generation does not promise automatic expiry or deletion. Cancel an unwanted open draft with `cancelDraft()`. Downloading the XML does not execute a bank payment.

See the [generation example](https://github.com/isecurefi/isecure-ts-client/tree/main/examples/processing-generate-file) and [approval/upload example](https://github.com/isecurefi/isecure-ts-client/tree/main/examples/processing-manual-upload). The destination environment determines its signing credentials; generating XML in Processing production does not require using production credentials when later submitting it to a bank test channel.
